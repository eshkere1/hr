> **Куда вставить:** в Lovable → значок проекта → **Settings → Knowledge**.
> Этот текст читается моделью перед каждым запросом. Он не про «сделай экран»,

## Что мы строим

**Растим** — платформа найма. Отраслево-нейтральная: направление, уровень,
навыки, документы для оформления, практическая проверка — эти понятия
одинаково работают и для разработчика, и для продавца, и для бухгалтера.

Под конкретную отрасль настраиваются справочники, а не структура:
направления и навыки в `src/lib/matching.ts`, воронки и причины отказа
в `sql/06_seed.sql`, обязательные документы — полем вакансии.

Продаём не «ИИ» — ИИ есть у всех. Продаём два измеримых числа:
**срок закрытия вакансии** и **отсев на испытательном сроке**.

Главный барьер — не конкуренты, а возражение HR: «мне придётся заполнять
систему». Выигрывает тот, у кого данные попадают в систему сами.

## Стек

- React 18 + TypeScript + Vite
- Tailwind CSS + shadcn/ui
- **PostgreSQL** через Supabase (Lovable Cloud): auth, RLS, storage, edge functions
- Клиент ходит в базу через `supabase-js`, никакого своего бэкенда
- Русский язык интерфейса. Даты — `dd.MM.yyyy`, деньги — `78 000 ₽`

## Пять принципов продукта

Каждый вырос из возражения конкретного стейкхолдера, а не из вкуса. Когда
два решения спорят — выигрывает то, которое ближе к этим принципам.

1. **Ноль ручного ввода.** Главное возражение HR — «мне придётся заполнять
   систему». Поэтому на каждом экране сначала показываем заполненное, а поля
   для ручного ввода прячем под «уточнить». Пустая форма — крайний случай,
   а не стартовый экран.
2. **Один экран — одно решение.** Экран существует, чтобы человек решил:
   звать или нет, двигать или нет, платить столько или меньше. Всё, что не
   помогает этому решению, уходит во вкладку.
3. **Показываем основание, а не балл.** Не «7,4 балла», а «закрыто 4 критерия
   из 6 — вот какие и чем подтверждены». Балл без основания HR не защитит
   перед руководителем.
4. **Разные экраны под роль.** Владельцу — дашборд, HR — воронка, руководителю
   подразделения — только его вакансии на телефоне. Одинаковый экран для всех
   означает форму на 20 полей, которую никто не заполнит.
5. **Тишина — это ошибка.** Любое ожидание получает срок и видимый статус —
   и для кандидата, и для руководителя. Если система молчит дольше нормы,
   это состояние интерфейса, а не отсутствие событий.

## Незыблемые правила безопасности

Нарушение любого из них — это дефект, а не стилистика.

1. **Роли не хранятся в `profiles` и не приходят с клиента.**
   Только таблица `public.user_roles` + функция `public.has_role()`.
   Если роль лежит в профиле, любой пользователь сделает себя суперпользователем
   обычным `UPDATE`.
2. **RLS включён на каждой таблице**, и у каждой таблицы есть политики.
   Скрыть поле на фронте — не значит скрыть: его видно в сетевом запросе.
3. **Все функции доступа** — `SECURITY DEFINER`, `STABLE`, `SET search_path = public`.
   Без этого RLS уходит в бесконечную рекурсию.
4. **Зарплата, заметки и оценки живут в отдельных таблицах** со своими
   политиками (`vacancy_compensation`, `application_compensation`,
   `candidate_notes.visibility`). RLS в PostgreSQL построчный, а не по колонкам,
   поэтому «кто какие поля видит» решается разделением таблиц.
5. **Ключи ИИ и job-бордов — только в edge functions**, через секреты.
   Ни один ключ не попадает в клиентский бандл.
6. **Аудит.** Изменения вакансий, откликов, вилок, ролей, офферов и согласий
   пишутся в `audit_log`. Читать журнал может только суперпользователь.

## Семь ролей

| Роль | Кто это | Что видит |
|---|---|---|
| `superuser` | Технический администратор | Всё. Единственный, кто раздаёт роли и читает аудит |
| `director` | Руководитель, владелец | Дашборд по компании, согласование вакансий и офферов, деньги |
| `hr_manager` | HR-менеджер | Воронка, база кандидатов, переписка, документы. Основной пользователь |
| `dept_head` | Руководитель подразделения | **Только свои вакансии и отклики по ним.** Вилку по своим — видит. Базы и общей аналитики — нет |
| `line_manager` | Непосредственный руководитель | Свои вакансии, свои интервью, своя команда. Вилку не видит |
| `employee` | Сотрудник | Своя карточка, свой ИПР, материалы, рефералы, мнение о кандидате |
| `candidate` | Кандидат | Только свои отклики, свои документы, своя переписка |

Одному человеку можно выдать несколько ролей. Роли `dept_head` и `line_manager`
ограничиваются подразделением через `user_roles.department_id`.

**Проверка при каждом новом экране:** что увидит на нём `dept_head` чужого
подразделения и что увидит `candidate`. Если ответ «всё» — экран сделан неверно.

## Модель данных: девять узлов

Полная схема — в папке `sql/`. Здесь то, что нужно держать в голове.

```
requisitions ──> vacancies ──> vacancy_criteria (5–6 критериев)
   заявка          вакансия         │
   за 3 мин                         │
                                    ▼
candidates ──> applications ──> application_criteria_results
  человек        ОТКЛИК            «4 из 6» + ЧЕМ подтверждено
  навсегда         │
                   ├──> conversations ──> messages      (Телеграм)
                   ├──> interviews ─────> ai_summary     (саммари встречи)
                   ├──> assessments ────> assessment_reviews (фидбек по ценностям)
                   ├──> offers ─────────> contracts
                   └──> application_stage_history        (где ломается воронка)
```

**Ключевые решения, которые нельзя переигрывать:**

- **Кандидат и отклик — разные сущности.** Человек откликается на несколько
  вакансий в разное время; через пять лет откликнулся снова — вся история
  общения на месте. Это фундамент, ошибка здесь дороже всего.
- **Критерии живут результатами, а не баллом.** В
  `application_criteria_results` у каждого критерия есть `evidence` (цитата
  или ссылка) и `source` (резюме, интервью, кейс, практическая проверка). Интерфейс
  показывает «4 из 6», клик раскрывает — какие и чем подтверждены.
- **Этапы — данные, а не константы в коде.** `pipelines` + `pipeline_stages`,
  потому что у разных должностей свои воронки: у линейной роли короткая,
  у ключевой — с практической проверкой. Цвет этапа хранится как **токен**
  (`stage-3`), а не как hex.
- **Обязательные документы задаёт вакансия**, а не код. `vacancies.required_documents`:
  у разработчика это паспорт, СНИЛС и ИНН, у того, кто работает с деньгами
  клиентов, добавляется проверка службой безопасности. Пока они не закрыты,
  перевод на оффер блокируется.
- **Отказ — это сегмент архива, а не конец.** Четыре сегмента: «не сейчас»,
  «не наш профиль», «не готов», «стоп-лист». Причина — обязательное поле из
  справочника `rejection_reasons`, а не свободный текст. Без сегментации архив
  превращается в свалку, а не в ресурс.
- **Согласия — отдельная таблица с журналом.** Без согласия на запись созвона
  разбор встречи незаконен. Отзыв — в один клик.

## Что делает ИИ и где проходит граница

ИИ **предлагает**, человек **подтверждает**. Ни одно действие, которое видит
кандидат, не уходит без подтверждения человека — кроме автоответов бота,
явно помеченных как ассистент.

| Что | Куда пишет | Кто подтверждает |
|---|---|---|
| Парсинг резюме → профиль | `candidates`, `candidate_profiles` | HR одной кнопкой |
| Разбор по критериям вакансии | `application_criteria_results` | HR подтверждает `confirmed_by` |
| Саммари и выводы по интервью | `interviews.ai_summary` | HR правит текст |
| Обратная связь по кейсу через **наши ценности** | `assessment_reviews` | HR подтверждает перед отправкой |
| Причина отказа из переписки | `applications.rejection_reason_id` | HR подтверждает одним кликом |
| Подбор 5 кандидатов из архива | `ai_jobs` | HR решает, кому написать |
| Поиск на естественном языке | `ai_jobs` + `candidates.embedding` | — |

Сообщения от ИИ в переписке **всегда помечены визуально** (пунктирная рамка,
подпись «ассистент»). Человек обязан понимать, с кем говорит.

## Границы MVP

**Делаем сейчас:** воронка и канбан, профиль кандидата, отклик, критерии
с основанием, Телеграм-переписка, саммари интервью, ИИ-фидбек по ценностям,
заявка на подбор и согласование, SLA и эскалация, документы для оформления,
практическая проверка, справочник отказов, дашборд, роли и права, согласия.

**Второй этап:** интеграции с hh/Avito/SuperJob, календарь и самозапись,
оффер с согласованием, зарплатная аналитика, мобильный доступ, API.

**Отдельный продукт, не тащим в MVP:** онбординг 30/60/90, ИПР,
наставничество, реферальная программа, сообщество. Таблицы под них есть
(миграция 04), интерфейс — потом.

## Тон текстов

- По-русски, без канцелярита и без англицизмов там, где есть русское слово.
- Кнопка называет результат: «Отправить оффер», а не «ОК».
- Ошибка объясняет, **что не так и что сделать**, без извинений и без
  «неверный формат». Пример: «Выше утверждённой вилки на 17 000 ₽.
  Согласуйте с руководителем или снизьте предложение».
- Пустой экран — подсказка, а не извинение: называет одно действие, которое
  имеет смысл сделать прямо сейчас.
- Отказ кандидату — внятный, с причиной, без «вы нам не подходите».

## Чего не делать

- Не создавать таблицу без RLS-политик.
- Не показывать общий балл вместо перечня закрытых критериев.
- Не писать цвета напрямую (`bg-blue-500`, `text-white`, hex) — только токены.
- Не делать один экран для всех ролей.
- Не отправлять кандидату ничего, не проверив `can_touch_candidate()`.
- Не записывать созвон без записи в `consents`.
- Не удалять данные кандидата физически, минуя `deletion_requests`.
- Не хранить ключи ИИ и job-бордов на клиенте.
