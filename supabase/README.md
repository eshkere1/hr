# Серверная часть: боты-мессенджеры

Ботов может быть несколько. Один бот на компанию — допущение, которое
ломается почти сразу: массовый подбор говорит не тем тоном, что точечный,
у филиала свой аккаунт, под кампанию заводят отдельный. Поэтому бот — это
строка в таблице `messenger_bots`, а не переменная окружения, которую
меняют переразвёртыванием.

| Функция | Кто её вызывает | Что делает |
|---|---|---|
| `telegram-webhook` | Телеграм | Ведёт весь диалог с кандидатом |
| `telegram-send` | Database Webhook на `INSERT` в `messages` | Доставляет ответ рекрутера через того же бота, проверив лимит касаний |
| `bot-register` | Приложение, экран «Боты» | Проверяет токен, придумывает секрет, регистрирует адрес и меню команд |

## Что умеет бот

Номера — фишки из исходной таблицы.

| Команда | Фишка | Что делает |
|---|---|---|
| `/start` | 61 | Объясняет, зачем нужны данные, и берёт согласие кнопкой |
| `/status` | 42 | Где отклик сейчас и до какого срока обещан ответ. При отказе — формулировка из справочника причин, а не «вы нам не подходите» |
| `/vacancies` | 11 | Открытые вакансии с честным «что реально будет в первый месяц», отклик в одно нажатие |
| `/slots` | 34 | Свободные окна руководителя, запись без согласований. Двое нажали на одно окно — выигрывает первый |
| `/test` | 10, 36 | Задание вопрос за вопросом прямо в переписке |
| `/docs` | 50 | Что нужно для оформления и чего не хватает |
| `/privacy` | 61, 62 | Отзыв согласия и запрос на удаление данных |

**Бот не выдумывает.** Каждый ответ собран из строк базы. На вопрос, ответа
на который в базе нет, он говорит «передал рекрутеру» — и передаёт. Бот,
сочинивший вилку или срок, стоит дороже, чем пауза до ответа человека.

**Ответ бота не считается касанием.** Лимит (фишка 41) существует, чтобы мы
не долбили человека, который нас не звал. Ответ на прямой вопрос — не дожим:
инициатива его. Иначе бот сжигал бы недельный лимит за три вопроса, и живой
рекрутер потом не смог бы написать.

## Три решения, которые стоит знать

**Приложение не знает про Телеграм.** При отправке оно пишет строку
в `messages`. База — источник правды, доставка — отдельная забота. Поэтому
сообщение уйдёт одинаково, откуда бы его ни отправили: из мессенджера, из
карточки кандидата, из автодействия этапа или из будущего автопилота. Одна
точка выхода вместо четырёх.

**Диалог помнит своего бота.** Отвечать нужно из того аккаунта, в который
человек написал: ответ от незнакомого бота кандидат либо не получит, либо
примет за спам. Поэтому у `conversations` есть `bot_id`, и `telegram-send`
берёт токен именно оттуда.

**У каждого бота свой адрес и свой секрет.** Адрес несёт id бота:

```
/functions/v1/telegram-webhook/<id бота>
```

По нему функция и понимает, кто принимает. Секрет тоже свой у каждого —
утечка одного не открывает остальных.

## Подключение бота

Через интерфейс: **Настройка → Боты → Подключить бота**. Одно поле.

1. В Телеграме `@BotFather` → `/newbot`, придумать имя и адрес
2. Скопировать выданную строку целиком
3. Вставить в поле и нажать «Подключить»

Дальше функция `bot-register` сама спросит у Телеграма, живой ли токен,
сгенерирует секрет вебхука в допустимом наборе символов, положит бота
в базу и вызовет `setWebhook`. Ни `curl`, ни терминала, ни ручной
подстановки секретов.

Токен уходит на сервер по HTTPS и остаётся в базе под RLS: читать его
может только суперпользователь, а функции доставки ходят под служебным
ключом. В браузер токен не возвращается — в списке видно последние шесть
символов, чтобы отличить одного бота от другого.

### Если бот перестал отвечать

Кнопка **Проверить** на карточке спрашивает у Телеграма `getWebhookInfo`
и показывает, что он думает: сколько сообщений в очереди и какая была
последняя ошибка. Она же пишется в карточку сама, когда доставка падает —
чтобы «кандидат не отвечает» не путали с «бот сломался».

## Первичная настройка проекта

Делается один раз.

### 1. Миграции

Файлы из [../sql](../sql) по порядку, последние — `08_messenger_bots.sql` и `09_bot_replies.sql`.

### 2. Выкладка функций

Панель Supabase → **Edge Functions** → **Deploy a new function** → **Via
Editor**, по одной на каждую из трёх. Либо через CLI:

```bash
supabase functions deploy telegram-webhook
supabase functions deploy telegram-send
supabase functions deploy bot-register
```

`verify_jwt` задан в [config.toml](config.toml). При выкладке через панель
его нужно выставить руками в настройках функции: у `telegram-webhook`
выключить (Телеграм не умеет присылать JWT, защита там своя — секретный
заголовок), у двух остальных оставить включённым.

### 3. Доставка исходящих

**Database → Webhooks → Create a new hook**

| Поле | Значение |
|---|---|
| Table | `messages` |
| Events | `Insert` |
| Type | Supabase Edge Function |
| Function | `telegram-send` |

Authorization панель подставит сама.

Требует расширения `pg_net` — оно включается вместе с интеграцией
Database Webhooks.

## Как проверить, что работает

1. Подключите бота на экране «Боты» — он сразу появится со статусом «на связи».
2. Напишите ему что-нибудь со своего аккаунта.
3. Откройте **Мессенджер** — там появится новый диалог, а в базе карточка
   кандидата с вашим `telegram_user_id`.
4. Ответьте из мессенджера или прямо из карточки человека. Ответ придёт
   в Телеграм от того же бота.

Если тишина — **Edge Functions → telegram-webhook → Logs**.

## Что осознанно не сделано

**Автопилот (фишка 12).** Функция кладёт сообщение в базу, но не отвечает
сама. Для этого нужен ключ модели и отдельное решение о том, где проходит
граница: на какие вопросы ассистент отвечает сам, а какие обязан передать
человеку. Ошибиться здесь дороже, чем не сделать — бот, наврав про
зарплату, стоит и кандидата, и репутации.

**Вложения.** Принимаем только текст и подписи к файлам. Резюме файлом,
фото документов и голосовые проходят мимо: для них нужно хранилище и
решение, что с ними делать дальше. Бот честно просит «пришлите сюда», но
пока такое сообщение увидит только рекрутер — автоматически в
`candidate_documents` оно не ляжет.

**Дожим по расписанию (фишка 13).** Бот отвечает, но сам не напоминает
о себе через день молчания. Для этого нужен планировщик, а вместе с ним —
правила, кого и сколько раз можно трогать. Лимит касаний в базе уже есть,
не хватает того, кто будет по нему ходить.

## hh.ru (фишка 30)

Вакансия заводится один раз — в системе — и уходит на hh кнопкой. Отклики
возвращаются в ту же воронку, где лежат отклики из Телеграма и из архива.
Рекрутер перестаёт вести две системы и переносить людей копированием.

| Функция | Кто вызывает | Что делает |
|---|---|---|
| `hh-oauth` | Экран «hh.ru» | Подключает работодателя, обновляет доступ, тянет справочники |
| `hh-publish` | Карточка вакансии → Публикация | Публикует, обновляет и снимает вакансию |
| `hh-sync` | Кнопка и расписание | Забирает отклики и заводит их как обычные |

### Секреты

**Edge Functions → Secrets**, три штуки:

| Имя | Откуда |
|---|---|
| `HH_CLIENT_ID` | Кабинет приложения на dev.hh.ru |
| `HH_CLIENT_SECRET` | Оттуда же |
| `HH_REDIRECT_URI` | Ровно тот адрес, что указан в заявке |

Redirect URI должен совпадать с заявкой символ в символ — hh сверяет строку
целиком и на расхождение отвечает отказом без объяснения.

### Три решения

**Токены в базе, а не в переменных окружения.** Работодателей может быть
несколько — филиалы, разные юрлица. И главное: hh выдаёт одноразовый
refresh_token. После обмена старый умирает немедленно, новый нужно сохранить
сразу, иначе доступ потерян. Из переменной окружения так не сделаешь.

**Функция не догадывается.** hh хранит регион и профессиональную роль
числами. Система подбирает их по городу и направлению, но если не нашла —
возвращает внятную ошибку вместо того, чтобы подставить «Москва» и «Другое».
Вакансия, опубликованная не в том регионе, стоит денег и приводит не тех.

**Ошибки hh переводятся.** Он отвечает массивом кодов вроде
`[{type: "not_enough_purchased_services"}]`. Человеку это ничего не говорит,
поэтому частые случаи разобраны словами: «у работодателя закончились
оплаченные публикации».

### Чего нет

**Резюме файлом.** hh отдаёт его структурой, но хранить чужие персональные
данные без нужды не стоит. Забираем контакты для связи и ссылку, по которой
рекрутер откроет полное резюме на hh.

**Обратная синхронизация статусов.** Приглашение и отказ пока не уходят на
hh — кандидат видит там прежний статус. Методы известны, дело за решением,
какие наши этапы каким статусам hh соответствуют.
